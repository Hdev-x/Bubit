# 기술 문제 해결 기록

개발 과정에서 해결한 문제의 원인·수정·검증을 기록합니다. 사용자에게 보이는 변경은 [변경 이력](../CHANGELOG.md), 이용 중 문제 신고는 [지원 안내](../SUPPORT.md)를 참고하세요.

## 늦은 REST 응답이 실시간 봉을 되돌리는 문제

**상황:** REST refresh를 시작한 뒤 WebSocket이 현재 봉을 갱신했는데, refresh 응답이 도착하면서 가격·거래량이 과거 값으로 바뀔 수 있었습니다.

**원인:** REST 응답을 받았다는 사실만으로 최신 상태라고 취급했습니다. 수신 순서와 데이터가 관측된 순서는 다릅니다.

**해결:** refresh 요청마다 WebSocket이 갱신한 봉과 필드를 기록합니다. REST 응답을 합칠 때 해당 OHLC·거래량은 현재 값을 보존하고 나머지 과거 봉은 보정합니다. 시가는 별도 상태에 중복 저장하지 않고 최신 캔들에서 계산합니다.

**검증:** `useCoinCandles.test.tsx`에서 REST 대기 중 WS 갱신, 과거 봉 보정, 현재가·시가 일치를 검증합니다. KRW 거래량 폴링과 refresh의 교차 응답도 검사합니다.

## 종목을 바꿨는데 이전 데이터가 다시 나타나는 문제

**상황:** A→B→A처럼 빠르게 이동하거나 화면을 나간 뒤, 이전 요청 또는 구독 callback이 늦게 실행될 수 있습니다.

**원인:** 종목 이름만 확인하면 처음 A 요청과 나중 A 요청을 구분하지 못합니다. 구독 해제를 호출해도 이미 대기 중인 callback은 실행될 수 있습니다.

**해결:** 거래소·상품·종목·시간봉 식별자에 요청 세대를 함께 사용합니다. 종료된 구독의 callback은 무시하고, 폴링 요청은 timeout·동시 실행 방지·cleanup을 갖춥니다.

**검증:** `useCoinCandles.test.tsx`, `useRealtimePrices.test.tsx` 및 차트 전환 테스트에서 역순 완료, 재시도, 비활성화·unmount를 재현합니다.

## 목록 전환과 실시간 중계 비용

**상황:** 거래소 전환·첫 관심종목 추가에서 목록이 늦게 표시되고, 전체 종목의 빈번한 갱신이 화면과 서버에 불필요한 일을 만들었습니다.

**해결:** 시장별 목록 요청·캐시를 공유하고 기존 데이터가 있으면 먼저 표시합니다. 40개 단위의 표시 범위와 화면 주변 렌더링·구독 범위를 구분합니다. 서버는 활성 구독을 추적하고 종목별 최신 값을 모아 중계합니다. REST 목록 자체를 40개씩 받는 서버 페이지네이션은 아닙니다.

**검증:** `marketTickerLists.test.ts`가 요청 공유·캐시 동작을, `MarketPanel.test.tsx`가 목록 표시·구독 범위를 검사합니다. `TickerSubscriptionsTest`가 활성 구독 집계를 확인합니다. 전체 브라우저 체감 속도에 대한 동일 조건 전후 개선율은 제시하지 않습니다.

## 지표를 꺼도 차트 전환이 느린 문제

**상황:** 기본 캔들이 준비돼도 일봉 같은 보조 응답을 기다리며 화면 표시가 지연됐습니다.

**해결:** 기본 캔들·현재가와 후속 보강 데이터를 분리하고 중복 일봉 요청 및 요청 전 대기를 제거했습니다. 같은 조건으로 이미 진행 중인 요청은 공유합니다. 마켓 상세를 열 때마다 전체 차트를 미리 받는 방식은 사용하지 않습니다.

**검증:** 요청 횟수·진입 대기·실패 후 재시도·종목 식별자 보호를 테스트합니다. 실제 PC·Mobile 전체 체감 속도의 동일 환경 전후 측정은 완료하지 않았으므로 개선율을 제시하지 않습니다.

## CSS를 나누면서 스타일 우선순위가 바뀌는 문제

**상황:** 큰 CSS 파일을 컴포넌트별로 옮기면 선언 내용이 같아도 import·번들 순서가 달라져 배경·배치가 바뀔 수 있습니다.

**해결:** 공용 규칙은 한 곳에서 관리하고 셸 CSS를 컴포넌트보다 먼저 import합니다. 앱별 값 차이는 CSS 변수로 표현합니다.

**검증:** `npm run check:css`가 규칙 순서, 진입점 import, 번들 순서, 주요 최종 선언·media 조건, 두 앱 셸의 클래스 중복을 검사합니다. 빌드 후 실행해야 번들 검사까지 수행합니다.

## 실행형 JAR 전환 후 제한된 지속 부하 관찰

JSP와 외부 WAS를 사용하지 않는 실행 구성에 맞춰 `bootJar`와 내장 서버로 패키징했습니다. 아래는 2026-10-16의 v0.2.2 공개 시세 조회 부하 관찰이며, WAR보다 빨라졌다는 비교 결과가 아닙니다.

| 조건 | 범위 |
| --- | --- |
| 시간 | 기준 2분 → 부하 15분 → 회복 3분, 총 20분 |
| 연결 | 2 → 4 → 8개, 최대 8개를 약 13분 유지, 1개 연결을 의도적으로 재접속 |
| 구독 | 연결당 45 topic, 최대 360개 구독; Bitget 주요 선물 종목과 Bitget·Binance BTC 현물/선물 시세 및 1분봉 |
| HTTP | PC·Mobile 문서, 비로그인 인증 응답, 공개 선물 목록 조회 |
| 환경 | 2 vCPU, CPU는 두 vCPU 전체를 100%로 계산 |

| 결과 | 관찰값 |
| --- | --- |
| 메시지 | 1,100,572건, 재접속을 포함한 각 연결에서 45 topic 수신 |
| HTTP | 399회 모두 예상 상태 코드; 비로그인 인증 조회는 401이 정상 |
| CPU | 기준 평균 3.76% → 부하 평균 9.06% / 최대 11.64% → 회복 평균 3.69% |
| 프로세스 RSS | 부하 중 약 417–423 MiB, 회복 끝 약 431 MiB |
| 열린 파일 수 | 기준 52–53 → 부하 최대 64 → 회복 끝 52 |
| 오류 | HTTP·WebSocket 오류, 예상 외 연결 종료, 서비스 재시작 0건 |

부하 종료 후 CPU와 열린 파일 수는 기준 수준으로 돌아왔습니다. RSS가 원래 값으로 돌아왔다고 해석하지 않으며, 이 시간 범위만으로 메모리 누수 부재를 보장하지 않습니다. 메시지 수신 간격은 거래소 송출 주기를 포함하므로 종단 간 지연으로 해석하지 않습니다.

24시간 안정성·대규모 동시 접속·브라우저 렌더 성능·실제 주문·정밀 GC 분석은 이 관찰 범위에 포함되지 않습니다. 자동 테스트와 이 관찰은 실제 기기의 모든 프레임이나 네트워크 단절을 대신하지 않습니다.
