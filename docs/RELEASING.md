# 버전과 릴리즈 관리

## 저장소와 운영 배포

제품 개발·버전·서버 배포의 정본은 비공개 개발 저장소입니다. 이 공개 저장소는 포트폴리오용 선별 소스이며 운영 빌드나 배포 입력으로 사용하지 않습니다. 공개 갱신과 GitHub Release 발행은 운영 배포와 독립적으로 진행합니다. 공개본의 버전은 내보낸 제품 소스의 버전이며 현재 서버의 실행 버전을 보장하지 않습니다.

## 무엇을 어디에 기록하나

| 기록 | 역할 |
| --- | --- |
| [`apps/web/package.json`](../apps/web/package.json)의 `version` | 제품 버전 정본. 화면 푸터도 이 값을 사용 |
| [README](../README.md)·[사용 가이드](USER-GUIDE.md) | 현재 사용할 수 있는 기능과 시작 방법 |
| [CHANGELOG](../CHANGELOG.md) | 사용자 관점의 버전별 변경 이력 정본 |
| [`releaseNotes.ts`](../apps/web/src/app/shared/updates/releaseNotes.ts) | 푸터 업데이트 팝업에 표시하는 변경 이력 요약 |
| [GitHub Releases](https://github.com/Hdev-x/Bubit/releases) | 태그에 대응하는 버전과 CHANGELOG의 해당 내용을 게시 |
| [기술 문제 해결 기록](TROUBLESHOOTING.md) | 특정 문제의 원인·해결·검증을 개발자 관점에서 설명 |
| Issue·PR | 개별 요구 사항, 변경 내용과 검증 근거 |

PR을 merge하는 것은 소스 반영입니다. 버전 태그·Release 발행과 실제 서버 배포는 별도로 수행하고 각각의 결과를 확인합니다. 실제 제공 버전은 배포 기록의 버전·commit·산출물 식별자로 확인합니다.

## 버전 기준

- 장기 브랜치는 `main` 하나이며, 변경은 작업 브랜치와 PR로 통합합니다. 버전 기록을 위해 별도 `beta` 브랜치를 만들지 않습니다.
- 제품 버전 정본은 `apps/web/package.json`의 `version`입니다. 초기 기준점은 `0.1.0`이며 이번 푸터의 `v0.1` → `v0.1.0` 변경은 표기 표준화로, 버전 증가에 포함하지 않습니다.
- 앞으로 제품 코드·화면이 바뀐 승인된 배포에서는 **직전 실제 배포 버전**을 기준으로 오류 수정·UI 정리·리팩터링은 Patch, 기능 추가는 Minor, 호환성을 깨는 변경은 Major를 올립니다. 초기 `0.x`의 호환성 변경은 Minor로 올리고, 정식 출시 `1.0.0` 판정은 별도 사용자 결정으로 남깁니다.
- 혼합 변경은 가장 높은 등급으로 배포당 한 번만 올립니다. 같은 내용 재배포와 rollback은 대상 산출물의 기존 버전을 유지합니다.
- `apps/web`에서 `npm version <version> --no-git-tag-version --ignore-scripts` 등으로 `package.json`의 `version`과 `package-lock.json`의 최상위·`packages[""]` 버전을 함께 맞춥니다. 개발 원본에서 export한다면 `ops/public-source/overlay/apps/web/package-lock.json`의 두 버전 필드도 맞추되 Public 의존성 차이를 보존합니다.
- 변경 이력과 배포 증거에 제품 버전·commit·산출물 식별자를 기록합니다. 버전 증가는 승인된 배포에 포함되며, CI 실행·merge·태그·GitHub Release 발행 승인으로 확대하지 않습니다. 아래 태그 규칙은 발행 승인 후 적용합니다.
- 기능 추가·오류 수정·사용성 개선 등 사용자가 체감할 변경만 CHANGELOG와 `apps/web/src/app/shared/updates/releaseNotes.ts`에 함께 기록합니다. 단순 문구·오탈자 수정이나 내부 정리는 PR·작업 기록에만 남깁니다. 화면용 내역은 실제 해당 버전으로 기록하고 최신 항목을 맨 위에 두며, 모든 배포 버전에 항목을 만들 필요는 없습니다. 과거 내역은 보존합니다.
- Beta 태그는 `v0.1.0-beta`, 수정 버전은 `v0.1.1-beta`처럼 사용합니다. 기능 단위가 커지면 `v0.2.0-beta`처럼 올립니다. 정식 버전은 `v1.0.0`부터 시작합니다.
- Beta에서도 호환성이 바뀌면 설정·데이터·API·사용법에 미치는 영향과 필요한 조치를 변경 이력에 명시합니다. 이미 발행한 태그는 다른 commit으로 옮기거나 재사용하지 않습니다.
- 위 태그 번호는 **예시**이며 발행 이력이 아닙니다. API의 Gradle 버전은 산출물 메타데이터이므로 제품 버전과의 대응은 배포 증거에 함께 기록합니다.
- 태그는 공개 저장소의 검증된 commit을 가리킵니다. 서비스가 배포되면 Release에 배포 여부·시각·대상 버전을 별도로 적어 실제 제공 버전을 식별할 수 있게 합니다.

## 평소 변경을 쌓는 방법

1. 작업 브랜치에서 수정하고 PR에 목적·사용자 영향·검증 결과를 적습니다.
2. 사용자가 체감하는 기능, 오류 수정, 호환성 변경은 `CHANGELOG.md`의 `Unreleased`에 간결하게 기록합니다. `추가`·`개선`·`수정`·`알려진 문제` 중 해당하는 항목만 사용하며 빈 항목은 만들지 않습니다. 기능 제거·호환성·보안 변경은 해당 항목에서 영향과 필요한 조치를 명시합니다.
3. 내부 정리나 오탈자처럼 사용자 영향이 없는 변경은 PR에 변경 이력 생략 이유를 적습니다. commit마다 노트 한 줄을 만들지는 않습니다.
4. 사용법·설정이 달라지면 관련 문서도 같은 PR에서 갱신합니다. 원인 설명이 필요한 문제는 기술 문제 해결 기록에 추가하고 변경 이력에서 연결합니다.
5. 리뷰와 해당 PR의 최신 CI가 통과한 뒤 squash merge합니다. 이 단계에서는 아직 릴리즈하지 않습니다.

보안 수정의 공개 내용과 시점은 [보안 안내](../SECURITY.md)를 따릅니다. 미해결 취약점 세부 사항을 `Unreleased`나 공개 PR에 먼저 게시하지 않습니다.

### 항목 작성 기준

- 변경 항목은 “개선했습니다” 대신 “개선·추가·수정”처럼 간결한 항목형 표현으로 작성합니다.
- **추가:** 새로 할 수 있게 된 일을 설명합니다.
- **개선:** 기존 기능이나 이용 과정이 어떻게 나아졌는지 설명합니다.
- **수정:** 어떤 상황에서 생기던 문제가 해결됐는지 설명합니다.
- **알려진 문제:** 해당 버전에 남은 사용자 제약과 가능한 대처 방법을 안내합니다. 해결한 원인·구현·검증은 기술 문제 해결 기록에 남깁니다.

예를 들어 차트 오류 수정은 “비동기 로직 리팩터링”보다 “종목 전환 후 이전 종목의 데이터가 다시 표시되는 문제 수정”처럼 적습니다. 이는 작성 예시이며 새 수정이나 릴리즈 이력을 뜻하지 않습니다.

## 버전을 발행할 때

1. 포함할 변경·버전·알려진 제한과 배포 범위를 확정합니다. 사용자가 영향을 받는 설정·스키마 변경이 있으면 적용·복구 절차를 먼저 준비합니다.
2. 릴리즈 준비 PR에서 `Unreleased`의 대상 변경을 실제 버전·발행 예정일 아래로 옮기고 새 `Unreleased`를 남깁니다. 발행 전에는 준비 중임을 표시하고, 일정이 바뀌면 실제 발행일과 일치시킵니다. 최초 버전에는 CHANGELOG의 최초 소스 공개 기준점도 함께 검토해 포함 기능을 요약합니다. README·CHANGELOG·이 문서의 현재 발행 상태와 SECURITY의 지원 범위를 함께 갱신합니다.
3. [실행 가이드](SETUP.md)의 Web lint·test·Mobile/PC build·CSS 검사와 API test·bootWar, 필수 CI를 확인합니다. PC·Mobile의 로그인·마켓→차트·종목/시간봉 전환·드로잉·재연결과 선택적 계좌 조회를 해당 환경에서 확인합니다. 테스트의 H2/mock 결과만으로 실제 PostgreSQL·거래소 연동을 검증했다고 기록하지 않습니다.
4. 최신 `main`·PR head·CI·미해결 리뷰·변경 범위를 확인하고 준비 PR을 merge합니다. 실제 발행할 commit과 검증 대상이 일치하는지 다시 확인합니다.
5. 유지관리자가 발행을 승인한 뒤 해당 commit에 태그를 만들고 GitHub Release를 작성합니다. Beta는 **pre-release**로 표시합니다. CHANGELOG의 해당 버전 내용을 게시하고 검증 결과·알려진 제한·업데이트 방법·배포 여부를 덧붙입니다. 코드 목록만 있는 자동 생성 노트로 대체하지 않습니다.
6. 실제 태그·Release와 문서의 버전·날짜·링크가 일치하는지 확인합니다. 발행한 과거 항목은 계속 보존합니다. 중대한 정정은 수정 이유를 남깁니다.

## 외부 서비스 운영 참고

새 환경의 첫 배포에는 아래 준비와 배포 승인이 필요합니다. 이미 운영 중인 환경은 해당 배포 기록에서 서버·도메인·서비스 주소와 복구 대상을 확인합니다.

- 배포 환경: API/Web 경로·도메인·HTTPS, 실제 PostgreSQL, 서버 전용 Secret 주입과 접근 권한
- 복구: 검증된 산출물·commit 식별, DB 백업/복구 확인, 이전 버전으로 돌아가는 절차
- 관찰: 오류·지연·거래소 제한·WebSocket 재연결을 확인할 로그/지표와 알림 수신 담당자
- 이용 안내: 운영 주체·문의처·개인정보 처리와 보존/삭제 요청 절차, 필요 약관, 사용자에게 공개할 제한
- 배포 후 확인: PC·Mobile 주요 흐름·API·실시간 연결, 서비스 주소와 실제 배포 버전 표시

배포에 실패하면 Release 발행을 서비스 배포 성공으로 표기하지 않습니다. 원인과 실제 제공 중인 버전을 기록하고 fix 또는 revert PR로 복구합니다. DB·데이터 복구는 코드 되돌리기와 별도로 판단합니다.

GitHub의 Release·태그 관계는 [공식 안내](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)를 참고하세요.
